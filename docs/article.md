# Claude Codeで、複数の投資をまとめて将来資産を把握できるシミュレーターを開発しました

## A. 課題概要

### 課題情報

- **課題名**: Section 1.0 オリジナルシステム課題2 Claude Code を使ってオリジナルシステムを開発・公開（2個目）
- **難易度**: ★★☆☆☆（5段階で自己評価。1つ目より低めに感じたが、理由はDセクションで詳述）

### 課題要件

- **ペルソナ**：投資はしているが、将来どうなるか漠然と不安な人。特に、日本円だけでなく外貨建ての投資（海外の金融商品など）も持っていて、資産全体の把握が難しい人
- **解決したい課題**：通貨や開始時期が異なる複数の投資を横断して見る手段がなく、「結局トータルでいくらになるのか」が分からない。金融の専門知識やExcelでの複利計算を前提とするツールは、ズボラな人・忙しい人には続かない
- **提供する価値**：通貨・開始日が異なる複数の投資を自由に追加し、複利計算による将来の資産推移をまとめてグラフと数値で試算できるシンプルなWebアプリ

### 作ったもの

**資産形成シミュレーター** — 投資を自由に追加・削除でき、通貨別の為替レートを反映した合計資産を試算できるNext.js製Webアプリ

- リポジトリ: https://github.com/hirose27tec-create/asset-growth-simulator
- 本番URL: https://asset-growth-simulator-mu.vercel.app

| 機能 | 説明 |
|---|---|
| 投資リスト管理 | 投資を件数の制限なく自由に追加・削除。1件ごとにラベル・元本・積立額・利率・開始日・終了日を設定 |
| 通貨・為替レート | JPY / USD / GBP / EUR から投資ごとに通貨を選択。対円の概算レートは画面上で編集可能 |
| 日付ベースの複利計算 | 開始日（過去日付も可）〜終了日の経過年数（小数）をもとに、元本分＋積立分を複利計算 |
| 今日時点サマリー | 合計評価額・投下元本合計・運用益を、複数投資を為替換算した上で今日時点の数値として表示 |
| 合算グラフ | 投資ごとに色分けした積み上げエリアチャートで、資産推移を暦年ベースで可視化 |

## B. 実装内容

### 使用技術

| 領域 | 技術 |
|---|---|
| フロントエンド | React（TypeScript）、Next.js 16.3.0（App Router）、Tailwind CSS v4 |
| グラフ描画 | Recharts（積み上げエリアチャート） |
| バックエンド・DB | なし（フロントエンドのみで完結、認証・永続化は今回のスコープ外） |
| ツール・その他 | Claude Code（設計・実装・検証）、Git／GitHub CLI（`gh`）、Vercel CLI、Playwright（動作検証） |

### 実装した機能の詳細

#### 1. 投資リスト管理（追加・削除）

**何をしたか**：単一フォームだったUIを、投資を配列で管理する「投資リスト」形式に変更した。「＋ 投資を追加」ボタンで新しい投資カードを追加でき、各カードに「削除」ボタンを設置。1件ごとに `label` / `currency` / `principal` / `monthlyContribution` / `annualRatePercent` / `startDate` / `endDate` を持つ。

**なぜこうしたか**：ユーザーから「複数の投資をしている場合、それを踏まえた資産を知りたい」との要望があった。1つのシナリオだけでなく、実際のポートフォリオ（一般的な積立投資＋海外の個別投資など）を横断して見たいというニーズに応えるため。

**仕組み**：`useState<Investment[]>` で配列管理し、`updateInvestment(id, patch)` でイミュータブルに1件だけ更新、`addInvestment` / `removeInvestment` で追加・削除する。各投資のIDは `crypto.randomUUID()` で発行。

#### 2. 通貨・為替レート対応

**何をしたか**：各投資に通貨（JPY / USD / GBP / EUR）を設定できるようにし、対円の概算為替レートを画面上で編集できるパネルを追加した。

**なぜこうしたか**：ユーザーの実際の投資がポンド建てだったため。サーバーを持たない構成にする方針（今回のスコープ外に「DB永続化」を含めていた）のため、外部APIでリアルタイムレートを取得するのではなく、初期値を用意しつつ手動で上書きできる方式にした。

**仕組み**：`DEFAULT_EXCHANGE_RATES`（`{ JPY: 1, USD: 155, GBP: 195, EUR: 165 }`）を初期値に `Record<Currency, number>` のstateを持たせ、`toJpy(amount, currency, rates)` で円換算して合算する。

#### 3. 日付ベースの複利計算ロジック

**何をしたか**：当初「積立年数」を整数で入力する年次複利ループだった計算方式を、開始日・終了日から算出した**経過年数（小数）を指数にとる複利計算式**に書き換えた。

**なぜこうしたか**：ユーザーの実際の投資（3年ごとにロールオーバーする金融商品）の資産評価が、四半期や月単位ではなく「経過年数の実数値（例：28.41年）」をもとに計算されていたため、それに整合させる必要があった。

**仕組み**：`lib/calculateGrowth.ts` の `valueAt()` で、経過年数 `t = (対象日 - 開始日) / 365.25日` を求め、`principal * (1+r)^t + 積立分の年金現価相当額` で評価額を算出する。`investedAmountAt()` で元本ベースの累計投下額も同じ考え方で算出する。

```ts
const principalValue = investment.principal * Math.pow(1 + r, t);
const contributionValue =
  r === 0
    ? annualContribution * t
    : (annualContribution * (Math.pow(1 + r, t) - 1)) / r;
```

**検証**：実在する投資の数値（7,000ポンド・年利10%・経過28.41年で約104,922ポンド）を使って手計算スクリプトで検算し、誤差が数十ポンド程度（日数の丸め誤差程度）に収まることを確認した。

#### 4. 合算グラフ（投資ごとの色分け積み上げ）

**何をしたか**：複数投資の評価額を、全投資の開始年〜終了年をカバーする年次タイムラインで合算し、Rechartsの積み上げエリアチャートで投資ごとに色分け表示する。

**なぜこうしたか**：「複数の投資をしている場合、それを踏まえた資産を知りたい」「投資ごとに色分けした内訳も見たい」という要望に応えるため。

**仕組み**：`buildTimeline()` で全投資の最小開始年〜最大終了年をカバーする年次ポイント列を作り、各年末時点の `valueAt()` を `toJpy()` で円換算して合算する。`<Area>` の `dataKey` を投資IDに紐づけ、`stackId="1"` で積み上げる。

#### 5. デプロイ（GitHub連携＋Vercel）

**何をしたか**：`git init` → GitHubパブリックリポジトリ作成 → push → Vercelプロジェクト作成 → GitHub連携 → 本番デプロイ、という一連の流れを実施した。

**なぜこうしたか**：1つ目のアプリと同じ運用（pushするだけで自動再デプロイされる）にするため。

**トラブル対応**：
- 作業ディレクトリ名が日本語＋スペースだったため、`create-next-app .` が「name can only contain URL-friendly characters」で失敗。英数字の一時サブディレクトリにプロジェクトを生成し、中身をルートへ移動して回避した。
- `vercel git connect` が初回失敗（`Failed to connect ... Make sure you have access to the repository`）。原因はGitHub側にインストール済みのVercel Appが、対象リポジトリへのアクセスを許可されていなかったこと。GitHubの「Installed GitHub Apps」設定でリポジトリアクセスを追加してもらい、再実行して解決した。

### 工夫したポイント

- 実装前にMVPの機能範囲と「やらないこと（スコープ外）」を先に文章化して合意した（1つ目のスコープ管理でのつまずきを踏まえた対策）
- 計算ロジックは実在の投資の数値で検算し、正確性を担保した
- Playwrightでブラウザを実際に操作し、スクリーンショットで見た目を検証。一度「バグに見える」挙動があったが、待機時間を延ばして再確認し、アニメーション途中の誤認識と判明した
- ユーザーの実際の投資情報（実在する会社名・具体的な金額・日付）を含む参考資料は、内容を確認した上で `.gitignore` に個別追加し、公開リポジトリに含めない判断をした
- 追加要望（v2）は既存のMVPに無秩序に継ぎ足さず、改めて壁打ちしてから独立した要件として実装した

## C. 実装過程

### 開発の流れ

**1. テーマ決定と要件定義（壁打ち）**

やったこと：「資産形成シミュレーター」と「目標達成支援アプリ（AIがマイルストーンを提案するようなもの）」の2案を比較検討。ドメインの独立性と実現時間（1〜2時間）の観点から前者を採用した。実装前にMVP機能とスコープ外を明文化し、`docs/requirements.md` にまとめた。

なぜこの方法を選んだか：1つ目の課題で「要件定義・スコープ管理」につまずいたと事前にヒアリングしていたため、着手前に決めるべきことを先に決め切る方針にした。

**2. Plan Modeでの実装プラン作成・承認**

やったこと：技術スタック・計算方式（当初は年次複利）・ディレクトリ構成・検証方法を1枚のプランにまとめ、Claude CodeのPlan Modeで承認を取得した。

なぜこの方法を選んだか：壁打ちで大きな決定を先に済ませていたため、Plan Mode承認後の手戻りがほとんど発生しなかった。

**3. 実装とビルド確認**

やったこと：`lib/calculateGrowth.ts` と `app/page.tsx` を実装し、`npm run build` でビルドエラーを都度解消（Rechartsの `Tooltip formatter` の型エラーなど）。Playwrightでブラウザを実行し、スクリーンショットで見た目を確認した。

なぜこの方法を選んだか：型チェックとビルド成功だけでは「実際に動いて見えるか」は分からないため、必ずブラウザ上での確認を挟んだ。

**4. デプロイ**

やったこと：GitHubリポジトリ作成→Vercel連携→本番デプロイ。連携時の権限エラーは、ユーザーにブラウザでの認可操作をお願いして解決した。

なぜこの方法を選んだか：1つ目と同じ運用方法（GitHub push→自動デプロイ）を踏襲するため。

**5. 追加要望対応（v2：複数投資・多通貨対応）**

やったこと：デプロイ後に来た「複数投資をまとめたい」という要望を、すぐには実装せず、通貨・日付・保存要否などを改めて壁打ちしてから実装に入った。

なぜこの方法を選んだか：最初に決めたスコープ外リストがあったからこそ、追加要望を「MVPへのなし崩し的な機能追加」ではなく「独立したv2要件」として扱う判断がしやすかった。

### つまずいたポイントと解決方法

**1. npmのプロジェクト名制限**

つまずき：作業ディレクトリ名が日本語＋スペースを含んでいたため、`create-next-app .` が「name can only contain URL-friendly characters」で失敗。

解決方法：英数字の一時サブディレクトリにプロジェクトを生成し、中身をルートディレクトリへ移動して回避した。

**2. Vercel-GitHub連携エラー**

つまずき：`vercel git connect` で「Failed to connect ... Make sure you have access to the repository」エラー。

解決方法：GitHubの「Installed GitHub Apps」設定で、VercelアプリにこのリポジトリへのアクセスをUser側に追加してもらい、再実行して解決した。CLIだけでは完結せず、ブラウザでの認可操作が必要なタイプのつまずきだった。

**3. グラフのアニメーションをバグと誤認しかけた**

つまずき：Playwrightで撮ったスクリーンショットで、積み上げグラフの一部が途中で縮んで見え、計算ミスを疑った。

解決方法：待機時間を延ばして撮り直すと正常な形になった。Node上の計算でも各投資の評価額が単調増加していることを確認し、Rechartsのアニメーション途中を捉えていただけと判明した。見た目の異常を疑う前に、まず「アニメーション中ではないか」を疑うのは今後も使える教訓。

**4. 個人情報を含む参考資料の置き場所ミス**

つまずき：投資の参考資料（実在する会社名・具体的な金額・日付入り）を、誤ってNext.jsのビルドキャッシュ（`.next/diagnostics/`、ビルドのたびに消える場所）に保存していた。

解決方法：`docs/references/` へ移動した上で、内容を確認して `.gitignore` に個別追加。公開リポジトリ（GitHub Public）に機微な個人情報が載らないようにした。
